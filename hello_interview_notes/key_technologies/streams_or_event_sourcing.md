# Ad hoc notes for Streams/Event Sourcing

## High level gists
1. Sometimes you'll be asked a question that requires either processing vast amounts of data in real-time or supporting complex processing scenarios, such as event sourcing. 
   1. Event sourcing is a technique where changes in application state are stored as a sequence of events. 
   2. These events can be replayed to reconstruct the application's state at any point in time, making it an effective strategy for systems that require a detailed audit trail or the ability to reverse or replay transactions.
2. In either case, you'll likely want to use a **stream**. 
   1. Unlike message queues, streams can **retain** data for a configurable period of time, allowing consumers to read and re-read messages from the same position or from a specified time in the past. 
   2. Streams are a good choice...
3. When you need to process **large** amounts of data in **real-time**. 
   1. Imagine designing a system for a social media platform where you need to display real-time analytics of user engagements (likes, comments, shares) on posts. 
   2. You can use a stream to ingest high volumes of engagement events generated by users across the globe. 
   3. A stream processing system (like Apache Flink or Spark Streaming) can process these events in real-time to update the analytics dashboard.
4. When you need to support complex processing scenarios like event sourcing. 
   1. Consider a banking system where every transaction (deposits, withdrawals, transfers) needs to be recorded and could affect multiple accounts. 
   2. Using event sourcing with a stream like Kafka, each transaction is an event that can be stored, processed, and replayed. 
   3. This setup not only allows for real-time processing of transactions but also enables the bank to audit transactions, rollback changes, or reconstruct the state of any account at any point in time by replaying the events.
5. When you need to support multiple consumers reading from the same stream. 
   1. In a real-time chat application, when a user sends a message, it's published to a stream associated with the chat room. 
   2. This stream acts as a centralized channel where all chat participants are subscribers. 
   3. As the message is distributed through the stream, each participant (consumer) receives the message simultaneously, allowing for real-time communication. 
   4. This is a great example of a publish-subscribe pattern, which is a common use case for streams.


## Things you should know about streams for your interview
1. Scaling with Partitioning: 
   1. In order to scale streams, they can be partitioned across multiple servers. 
   2. Each partition can be processed by a different consumer, allowing for horizontal scaling. 
   3. Just like databases, you will need to specify a partition key to ensure that related events are stored in the same partition.
